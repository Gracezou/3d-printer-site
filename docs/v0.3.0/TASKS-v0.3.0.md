## B0 · 基线与契约

- [x] 核对 `refund.service.ts`、现有后台退款 API/表单、`scripts/test-refunds.ts`、`order_items.bom_snapshot`、库存流水、`print_jobs` 和角色权限的当前语义；记录一组全额及部分退款基线结果。
- [x] 明确历史 `refunds`（无 `refund_items`）的读取与展示方式，迁移不回填虚构商品明细；现有 `test:refunds` 必须继续通过。
- [x] 确定同一 `order_item` 的多次/部分数量退款如何计算剩余可退数量、优惠尾差与运费最后一笔；以**累计实退金额 ≤ 实付金额**为数据库和服务层共同约束。
- [x] 定义支付提供方成功、数据库落账失败时的可重试/人工对账流程。提供方调用不可能与 PostgreSQL 事务原子提交，不得把外部退款成功误报为失败后直接重试出款。
- [x] 明确 `done` 商品的尺寸不符申请与普通 `queued` 准入如何并存：客户可提交例外申请，但只有后台有权越过打印状态限制并决定是否退款；申请本身不动钱、不动库存。

基线记录（2026-09-17）：现有 `refundOrder` 按总金额退款；全额时可返库、部分时不能返库；部分退款应保持 `paid` 等原状态。旧 `test:refunds` 的部分退款断言仍期望 `refunded`，与 `96126c5` 修复冲突，现已修正，实测通过。该脚本的部分退款样例**没有 `order_items`**，不能直接作为新商品级引擎用例。旧 `fn_refund_return_stock` 以整单为单位，库存流水也以订单为幂等维度，必须由后续 T203/T209 改为退款明细维度。支付提供方成功但本地提交失败目前仅记录日志，尚无自动对账/安全重试机制。

B0 契约结论：历史退款按原订单级记录展示，不伪造明细；若订单已有无明细的成功**部分**退款，商品级剩余可退量无法可靠推断，自动退款须拒绝并转人工对账。新退款对同一商品按“已退数量 → 本次数量”的累计区间计算金额；各商品优惠用累计比例分位，最后一笔全部商品退完时才计入运费，同时校验订单总可退余额。支付渠道成功但本地落账失败时保留原 `outRefundNo` 与待核对状态，禁止直接生成新退款号再次出款，需查询渠道结果后幂等补记或人工核对。普通申请只接收 `queued`；尺寸不符/装配原因允许客户提交非 `queued` 申请，但只有有权后台人员可放行。仅值零元的商品明细可随同一笔有金额退款处理；单独零元退货如何入账仍需在 T205 实现前明确，不用假造一笔 0 元支付渠道退款。

环境门禁（2026-09-17）：本地 `.env.dev` 与 `.env.production` 的数据库连接**指向同一 Supabase 数据库身份**。开发中只生成与检查迁移文件，不运行 `db:migrate` 或其他会写数据库的集成测试。T201 的数据库验收及 T203 的库存流水验收须在独立开发库/可恢复测试分支完成；绝不能用现网库冒充开发库。

## B1 · 数据与金额、库存（T201–T203）

### T201 商品级退款数据模型

- [~] 增加 `refund_items`、`return_requests`、`return_request_items`，按需求文档 §5 建立外键、检查约束、唯一约束和 `uq_return_pending_per_order` 部分唯一索引。Schema 与前向兼容迁移文件已生成并通过离线检查，尚未在独立数据库实际执行。
- [ ] `refunds` 继续代表一次退款操作；明细金额求和等于退款头金额，历史订单级记录保持可读。
- [~] 为申请单所有权查询和审核队列建立所需索引；新表启用 RLS，并收回 `anon`/`authenticated` 直接表权限，服务端使用既有数据库连接；实际 Data API 暴露/GRANT 状态待独立数据库验证。
- [ ] 迁移保持前向兼容，并验证全新数据库与既有数据数据库；生产执行前须建立 Supabase 可恢复点，本批开发不执行生产迁移。

### T202 金额分摊

- [~] 用 `decimal.js`/数据库 `numeric(10,2)` 计算各商品小计、按比例分摊的优惠、商品实退额；不用 JS 浮点数处理钱。纯函数与单元测试已完成，待接入持久化引擎。
- [ ] 部分退款不退运费；**最后一件/最后一份数量**退完时一次退剩余运费；订单跌破包邮门槛不追加收费。
- [~] 以累计余额做最后一项的分位兜底，不逐项独立四舍五入；已覆盖不同单价、优惠、运费、分批退同一商品、数量大于 1、接近全额折扣，零运费与更多边界待补。
- [ ] 红线测试：三件不同价格商品逐件退款，累计实退金额**精确等于订单实付金额**，且任一中间步骤均不超额。

### T203 按下单时 BOM 快照返库

- [~] 根据 `order_items.bom_snapshot` 与本次退款数量计算返还量，不使用当前商品 BOM；纯计算函数与单元测试已完成，数据库事务与 `refund_items.restock` 按件生效待接入。
- [ ] 部分退款也能返库；库存流水能追溯到唯一 `refund_item`，并与可售数量视图核对。
- [ ] 修改实时 BOM 后再退款，验证返还仍按旧快照；`restock=false` 与失败退款均不改变库存。

## B2 · 共用退款引擎（T204、T205、T209）

### T204 打印队列联动

- [ ] 仅在退款确认成功后，把对应仍为 `queued` 的打印任务移出待生产队列；`printing`、`post_processing`、`done` 不自动取消。
- [ ] 重放结果不重复移除；退款失败时队列保持原样。

### T205 `refundOrder` 商品级重构

- [ ] 输入改为订单商品、数量及逐件 `restock`，服务端重新计算金额；后台不能提交任意总额覆盖计算结果。
- [ ] 后台直接退款与申请审核通过共用同一引擎；保持支付 Provider 抽象，业务层不引用支付宝 SDK 类型。
- [ ] 全部商品退完设订单 `refunded`；部分退款保持原状态。针对 `96126c5` 的修复语义写回归测试。
- [ ] 支付成功后，退款头/明细、订单累计金额、库存流水、打印状态与审计记录具备一致的完成/补偿语义；失败不留下“已返库但未退款”的状态。

### T209 幂等、超额与并发

- [ ] 为一次退款及每条商品明细建立稳定幂等键；重复请求/回调不重复出款、记账或返库。
- [ ] 并发锁定订单商品可退余额；同一商品并发退款仅有一次成功，累计数量和金额不可超过原购买量及实付额。
- [ ] 多耗材库存锁按 `material_id` 升序；加入并发测试及重复回调测试。

## B3 · 客户申请与运营审核（T206–T208）

### T206 客户端退款申请

- [ ] 实现 `POST/GET /api/returns`、详情与取消接口；所有客户详情查询同时验证 `user_id`，只允许订单所有者申请/查看/取消。
- [ ] 订单详情按商品显示可申请数量、打印状态与申请入口，支持多商品/数量申请；提交仅创建申请，不触发退款或返库。
- [ ] 普通申请仅接受 `queued`；准入规则有集中可配置入口，不把规则散落在页面和 API 中。同一订单仅一条 `pending`，重复与不准入分别返回 40915/40916。
- [ ] 凭证上传复用既有安全校验、限额和权限；页面明示审核结果在订单中心查看，本期不发送邮件。

### T207 尺寸不符/装配例外

- [ ] 例外原因可由客户提交并在后台队列显著标记；`done` 商品能进入人工审核，但普通原因不得绕过准入限制。
- [ ] 后台对任何打印状态的例外申请可受理；是否返还库存仍由运营逐件判断，校验失败使用 40919。

### T208 后台审核队列

- [ ] 新增 `return:review` 并接入 RBAC、角色配置、审核列表与详情；无权限 API 返回 403。
- [ ] 审核页展示每件商品当前打印状态、已退/可退余额和逐件返库选择；通过时调用 B2 引擎，驳回记录原因。
- [ ] 审核状态、审核人/时间与 `admin_operation_logs` 同一数据库事务写入；并发审批或重复提交不能触发两次退款。
- [ ] 客户订单中心展示 `pending`、`rejected`、`completed` 等结果，已撤销申请不可再审核。

## 发布边界

开发验收通过 ≠ 允许上线真实资金。生产发布前须另做：数据库备份/恢复演练、迁移差异核对、v0.2.3 分支集成测试、支付生产资质与小额实单退款验证。v0.2.3 备案或延迟问题继续挂起时，v0.3.0 可以完成代码和沙箱验收，但不得顺手切换上海公网流量或生产支付通道。
