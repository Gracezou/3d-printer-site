## D. H13 二次核对方法（v0.2.2 T144 执行）

`deploy/release.sh` 已具备蓝绿发布能力（blue/green 槽位 + healthcheck + nginx upstream 切换 + 失败自动回滚），本项核对的是**构建产物内容**而非发布方式。

三条独立证据，任一不符即说明线上跑的不是新构建产物：

1. **健康接口版本**
   `curl -s https://printer.daxiaoxiang.com/api/health` → 构建 SHA 应等于当前分支 HEAD。
2. **服务器活跃镜像**
   `cat /opt/3d-printer-site/.active-release` → `ACTIVE_IMAGE` 的 `sha-` 后缀应与上一条一致。
3. **浏览器产物内的站点地址**
   线上 `_next/static` 的 JS 中应出现 `https://printer.daxiaoxiang.com`，
   **不应**出现 `188.239.16.176` 或任何 `http://` 旧地址。

> `.github/workflows/release-image.yml` 写法为 `${{ vars.PREPROD_SITE_URL || 'https://printer.daxiaoxiang.com' }}`，
> 即便仓库变量未设置，回退值也是正确的 HTTPS 域名。因此 H10 未配置不会导致构建出错误地址，
> 但仍建议显式设置，避免将来域名变更时踩坑。

## E. 战略级（无归属版本，需并行推进）

### E1 支付宝生产商户号与「扫码轮询」模式

**现状**：代码使用 `alipay.trade.page.pay`（电脑网站支付）+ `alipay.trade.query`（主动查询）+ `alipay.trade.refund`。异步通知已在 v0.2.1 验收通过，且已加入漏投补偿（commit `b475509`）。

**关于「申请支付链接 → 二维码扫码 → 前端轮询 → 后端查询支付宝状态」这一模式的评估**：

- 技术上仍可行，对应 `alipay.trade.precreate`（当面付 / 扫码支付），属于**独立签约的产品**。
- 它解决的问题是**异步通知到不了服务器**（无公网域名、回调被拦截）。而本项目已有 HTTPS 公网域名，H16 已验收通知可直达，并且主动查询补偿已经吸收了该模式的主要好处。
- **它不解决资质问题**：无论 `page.pay` 还是 `precreate`，都需要支付宝开放平台的生产商户号，该商户号所需的企业资质与网站要求一样都要满足。
- **结论：不建议为此改造。** 现有「异步通知为主 + 主动查询补偿」的组合已经覆盖了该模式能带来的可靠性收益，且复杂度更低。

**待核实（v0.2.3）**：境外域名 / 无 ICP 备案对支付宝生产商户号审核的实际影响。以支付宝开放平台当前官方说明为准。

### E2 支付方式扩展路线

**架构侧已就绪**：`payments.provider`（`varchar(30)`）已存在，`src/lib/services/payment/` 下已有 `provider.interface.ts`、`provider.factory.ts`。**接新支付方式零改表**，只是新增 Provider 实现 + 环境变量。这是 v0.1 设计约束（订单/库存 service 禁止引用支付宝 SDK 字段）的兑现。

**业务侧卡点在资质**：国内支付通道（微信支付国内商户号、银联商户、支付宝国内商户号）普遍要求营业执照 + 已备案域名。

若走跨境通道，优先级建议：

1. **微信支付（跨境）** —— 第二个应接入的通道。两个前提：一个 `mch_id` 对应**一种结算币种**；需要**微信公众号**才能取得 APPID。资质细则需联系微信支付跨境业务团队确认。
2. **银联国际 / 云闪付** —— 边际收益小得多，主要价值在信用卡受理，排在微信之后。
3. **Stripe / PayPal** —— 属于国际化阶段，当前已推迟（A1）。

> 方向性判断，非资质结论。各通道准入条件会调整，办理时以官方当前说明为准。

### E3 ⚠️ 备案与服务器位置的认知更正

**"重新申请域名并绑定"不能替代迁移。**

ICP 备案的核心要求是**网站接入的服务器必须位于中国大陆境内**，备案是「域名 + 境内服务器实例」的绑定关系。华为云确实提供域名服务，也能代办备案，但备案时需要绑定一个**境内**实例并使用其备案服务号。换一个新域名不改变服务器在新加坡这个事实，因此**换域名解决不了备案问题**。

因果链是固定的：

```
想要国内支付通道 → 需要生产商户号 → 需要备案域名 → 需要境内服务器
```

**但"迁移"未必像想象中那么重**。存在一个明显更轻的折中方案：

> **只迁应用，不迁数据库。** 应用部署到境内实例并完成备案，Supabase 继续留在新加坡。

代价是跨境数据库延迟。`TECH_SPEC.md` §13.2 与 `CHANGES-v0.2.0.md` §10 已经讨论过应对方式：把下单事务合并为单个存储过程，减少跨境往返次数。相比"新建境内 PostgreSQL + 对象存储 + Auth 实例 + `pg_dump`/`pg_restore` 全量迁移"，这条路径的工作量小一个量级。

**建议**：在决定"不迁"之前，先按这个折中方案重新评估一次成本。

### E4 上海实例备案资格

若采纳 E3 的折中方案，须先在华为云控制台核实 Flexus L 实例是否满足备案条件——部分规格不支持，不满足则需更换为标准 ECS。**这决定境内服务器的采购规格，建议尽早确认。**

### E5 多币种定价

`payments.currency` 已存在，但商品定价是单币种。已决 A22：暂时仅人民币结算，需求量明确后再拓展。届时需要独立价目表（product_prices by currency）+ 汇率来源与更新频率。

### E6 个人信息出境合规

已决 A23：由用户协议 + 明示同意处理，任务归 v0.4.0。

⚠️ **补充提醒**：明示同意是《个人信息保护法》对个人信息出境的**必要条件之一，但通常不是充分条件**。出境还可能涉及单独同意、告知境外接收方信息、个人信息保护影响评估等要求，具体适用取决于数据规模与类型。本条不构成法律意见，正式运营前建议咨询专业人士。

## G. 移动端购买栏范围（建议，待确认）

**建议：只在商品详情页做常驻底部购买栏。**

| 页面 | 建议 | 理由 |
|---|---|---|
| 商品详情 | **做常驻底部栏**，展示当前 SKU 价格 + 主操作 | 页面长、需要滚动看图文详情，用户选完规格后主操作可能已滚出视野。这是常驻栏收益最大的场景 |
| 购物车 | **不做常驻栏**，用页内 sticky 汇总条 | 购物车本身就是短页面，主操作天然靠近内容底部 |
| 结算页 | **不做常驻栏**，用页内 sticky 汇总条 | 结算页有大量表单输入，移动端键盘弹起时常驻底部栏会被顶起或遮挡输入框，是典型的体验陷阱 |

**共同要求**：适配 iPhone 安全区域（`env(safe-area-inset-bottom)`），避免被 Home 指示条遮挡。

三个页面都做常驻栏会让整站看起来像一个"到处是浮动条"的廉价模板，而且结算页的键盘冲突会实实在在制造 bug。

## H. 产品定位（A26 全文）

> **一家专做电子阅读器保护壳的按单打印店。**
> 覆盖阅星瞳、Kindle、掌阅、文石等主流品牌，也做已停产、大厂不再供货的老机型。
> **下一个开哪个机型，由需求量决定**——用户可登记意向，够人要就开模。

### H1 三层结构

| 层 | 内容 |
|---|---|
| 品类 | 电子阅读器保护壳（小挂件小玩具为周边，见 A27） |
| 差异 | 冷门机型与停产老款也有；按单打印，不压库存 |
| 参与 | 没有你的型号可以登记，需求量决定开模顺序 |

### H2 为什么这个定位成立

三个特征叠加，几乎是为 3D 打印量身定做的：

1. **机型碎片化到荒谬**——每个型号尺寸不同，壳不通用
2. **每个型号的市场都太小**——注塑开模要卖上千个才回本，厂商只做最热门的几款
3. **用户痛感强且无替代**——冷门型号和停产老款的用户往往全网买不到合适的壳

**护城河不是「我们按单生产」，而是「只有我们做这个型号」。** 按单生产退居第二位，作为支撑理由存在。

### H3 意向登记是引擎，不是附加功能

长尾生意最难的问题是「先做哪个 SKU」。意向登记一次解决三件事：需求验证、首批买家、**持续更新的内容供给**（投票榜、开模进度、新机型上线——这比任何前端花招都更能解决「首页新鲜度」问题）。

### H4 用户行为特征

用户**带着确定目标来**：他有一台什么机器，就要那台机器的壳。因此首页第一屏的核心是**设备选择器**，不是商品网格；站内 SEO 主力是**机型落地页**，不是商品列表。

### H5 已知的连带影响

| 影响面 | 说明 | 归属 |

### H6 延展机会

阅星瞳是**磁吸式**设备。磁吸生态可延展出支架、卡包、握把、配重等配件——这类配件同一用户可买多件，复购价值可能高于保护壳本身。X4 已上市，新机型上市初期是配件需求最旺、供给最少的窗口。

### H7 thin content 风险（重要）

机型页策略是「未开模机型也建页，抢占长尾词并收集需求」。但**大批只有标题、没有实质内容的页面会被判定为 thin content 或 doorway page，可能牵连整站权重**。

每个机型页必须有真内容：设备尺寸参数、接口位置、当前登记人数、相同尺寸可共用的其他机型、相关已开模商品。**页面可以没有商品，但不能没有内容。**

## I. 「书衣」商标风险（A37 详述）

### I1 已确认事实

「书衣」商标**已被他人注册**。经评估后决定沿用，属于**主动接受的风险**。

### I2 需要澄清的一处认知

决策讨论中提出「独立站不影响国内商标问题」。这一表述**并不准确**，记录在此以免后续基于该前提做进一步判断：

商标权确有地域性，但侵权认定看的是**是否在中国境内进行商业使用**，而非服务器位于何处。本站面向中国大陆用户、以人民币计价、通过支付宝收款、向大陆发货——这些事实在实践中通常足以构成境内商业使用。**服务器在新加坡不构成免责事由。**

真正成立的理由是另一条：**当前经营规模小，权利人主动维权的概率低**。这是一个合理的商业取舍，但它的成立依赖「规模小」这个前提——前提变化时结论需要重估。

### I3 风险触发条件

出现以下任一情况时，应重新评估是否更名：

1. 销量或站点知名度明显上升
2. 开始在国内平台投放推广（小红书、抖音、微博等）——曝光会显著提高被发现的概率
3. **SEO 开始见效**——注意这与 v0.2.2 的核心投入直接冲突：机型长尾词做起来的过程，本身就是提高被权利人发现概率的过程
4. **申请支付宝生产商户号时**——商户号审核需提交经营与品牌信息，与在先商标冲突可能影响审核结果。这条与 E1、E2 的既有规划直接相关

### I4 成本曲线

改名成本随时间急剧上升：

| 时点 | 成本 |
|---|---|
| **现在** | 近乎为零——改几份文档，代码尚未实现 |
| SEO 收录后 | 域名、外链、收录、站内文案全部重做，已积累的搜索排名归零 |
| 有老客户后 | 再加上品牌认知迁移与客户沟通成本 |

### I5 备选名（若将来需要更名）

均为生造组合词，非现成词汇，商标通过率相对更高：

| 名称 | 内涵 | 英文 |
|---|---|---|
| 抱卷 | 双手护着一卷书，即壳护着阅读器；与 H1「量卷裁衣」共用「卷」字 | Bookhold |
| 函衣 | 「函」为书函，「衣」为外覆 | Bookcase |
| 承卷 | 承托书卷 | Bearer |

> 不要走「书衣社」「书衣室」这类加后缀的路径——商标近似审查中通常仍会被判定与在先商标近似。
