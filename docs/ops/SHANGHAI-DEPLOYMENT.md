## 2. 2G 发布路径

新增 `deploy/release-low-memory.sh` 与 Compose 覆盖文件，采用以下流程：

1. 校验镜像必须为 `ghcr.io/...:sha-<commit>` 不可变标签；
2. 在旧容器仍运行时先拉取镜像；
3. 拉取成功后停止旧容器；
4. 以固定 `127.0.0.1:3000` 启动新容器；
5. Docker healthcheck 与 `/api/health` 同时通过后写入 `.active-release`；
6. 启动或健康检查失败时停止候选容器，并恢复 `.active-release` 中记录的上一镜像。

低内存覆盖参数：

- 容器上限 768 MiB，保留 384 MiB；
- Node.js Heap 上限 512 MiB；
- CPU 上限 1.5 核，PID 上限 256；
- 根文件系统只读，`/tmp` 使用 64 MiB tmpfs；
- 丢弃 Linux capabilities、禁止提权；
- json-file 日志 10 MiB × 5；
- 端口只发布到 `127.0.0.1:3000`。

## 4. 镜像分发风险

上海服务器可以认证并访问公开 GHCR 镜像，但跨境下载长时间只有几十 KB/s，直接拉取不满足可靠发布要求。本次演练使用以下临时中继：

1. 新加坡服务器导出同一不可变镜像；
2. 使用一次性 SSH 密钥及 SHA-256 校验并行分块传输；
3. 上海校验哈希后导入 Docker；
4. 立即撤销临时防火墙放行、授权公钥、私钥、压缩包和分块。

临时凭据与归档已全部删除。正式长期方案应优先使用境内镜像仓库（如华为云 SWR）或在 CI 同步推送国内 Registry；在该方案落地前，不能把上海直接拉取 GHCR 视为稳定的无人值守发布链路。
