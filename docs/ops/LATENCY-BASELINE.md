# 上海至新加坡 Supabase 延迟基线

> 状态：进行中，仅完成 2026-09-14 下午样本
>
> 时区：`Asia/Shanghai`
>
> 目标：Supabase 新加坡区，Supavisor `6543` transaction 模式

## 1. 方法

- 查询固定为 `SELECT 1`，不读取业务数据。
- 每个地点、时段分别采集 100 次冷连接和 100 次热连接。
- 冷连接包含 TCP/TLS/认证及首次查询；热连接复用单连接并在 5 次预热后计时。
- 上海目标机与现有新加坡生产机使用相同脚本、相同连接池端点和相同样本量。
- 原始 JSON 只包含脱敏位置、时段、连接模式与耗时，不包含连接串、账号或查询结果。

测量命令由 [`scripts/measure-db-latency.mjs`](../../scripts/measure-db-latency.mjs) 提供。脚本会拒绝非 `6543` 连接，避免用 5432 结果误判生产链路。

## 4. 阶段判断

下午上海热连接 p95 为 **68.06 ms**，按 v0.2.3 的 `<80 ms` 门禁，当前时段属于“正常”，暂未触发下单存储过程改造。冷连接 p95 为 **505.58 ms**，说明生产应用必须复用连接，不能采用每次请求新建数据库连接的运行方式。

这不是最终迁移结论。上午、晚高峰以及 L2 真实接口、L3 下单事务和“10 抢 5”并发验证均未完成；在这些证据补齐前不启动公网迁移。
