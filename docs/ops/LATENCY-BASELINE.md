# 上海至新加坡 Supabase 延迟基线

> 状态：L1 通过；L2/L3 已完成并触发暂停迁移门禁
>
> 时区：`Asia/Shanghai`
>
> 目标：Supabase 新加坡区，Supavisor `6543` transaction 模式

## 1. 方法

- 查询固定为 `SELECT 1`，不读取业务数据。
- 每个地点、时段分别采集 100 次冷连接和 100 次热连接。
- 冷连接包含 TCP/TLS/认证及首次查询；热连接复用单连接并在 5 次预热后计时。
- 上海目标机与现有新加坡生产机使用相同脚本、相同连接池端点和相同样本量。
- 原始 JSON 只包含脱敏位置、时段、连接模式与耗时，不包含连接串、账号或查询结果。

测量命令由 [`scripts/measure-db-latency.mjs`](../../scripts/measure-db-latency.mjs) 提供。脚本会拒绝非 `6543` 连接，避免用 5432 结果误判生产链路。

## 4. L1 门禁结论

上海热连接 p95 在上午、下午、晚高峰分别为 **72.74/68.06/76.31 ms**，全部低于 v0.2.3 规定的 80 ms 门禁；两地共 1200 次查询全部成功且无超时。

**L1 结论：正常，允许进入上海应用部署和 L2/L3 验证，不触发 `TECH_SPEC.md` §13.2 下单存储过程改造。**

冷连接 p95 为 491.86–505.58 ms，明显高于热连接，说明生产应用必须复用数据库连接，不能采用每次请求新建连接的运行方式。是否最终迁移公网流量仍取决于 L2 真实接口、L3 下单事务及“10 抢 5”并发验证。

## 5. L2 真实接口结果

两地均使用相同 v0.2.3 业务代码、本机 loopback 地址和 Supabase 项目。每类接口先预热 5 次，再采集 30 个有效样本；购物车使用临时 Supabase Auth 用户和真实 session cookie，测试结束后自动清理。商品列表与详情保留设计中的 60 秒共享缓存策略，实时库存明确为 `no-store`，没有用静态页面替代接口。

| 接口 | 新加坡 p50/p95/p99 | 上海 p50/p95/p99 | p95 跨境净增量 | 上海服务端 p95 |
|---|---:|---:|---:|---:|
| 商品列表 | 16.12 / 28.07 / 31.80 ms | 153.39 / 164.50 / 176.23 ms | 136.43 ms | 149.20 ms |
| X3 商品详情 | 14.16 / 15.89 / 16.03 ms | 145.38 / 154.69 / 156.16 ms | 138.80 ms | 149.20 ms |
| X3 实时库存 | 14.57 / 19.43 / 23.68 ms | 146.19 / 154.62 / 173.42 ms | 135.19 ms | 149.00 ms |
| 登录购物车 | 90.70 / 215.53 / 361.95 ms | 675.05 / 884.99 / 1032.53 ms | 669.46 ms | 878.70 ms |
| X3 机型页 | 23.93 / 28.00 / 31.15 ms | 292.91 / 297.09 / 315.14 ms | 269.09 ms | 290.60 ms |

所有样本 HTTP 状态均为 200、业务码均为 0，响应结构与大小保持一致。实时库存返回禁止缓存响应头；列表与详情返回预期共享缓存响应头。本机直接请求没有 CDN `Age` / `x-nextjs-cache`，因此数据反映应用与数据库路径而非边缘缓存命中。

购物车是唯一稳定超过 500 ms 慢请求阈值的 L2 接口，容器日志产生 `Slow API request` 记录。其 p95 跨境净增量约 669 ms，说明用户鉴权加购物车多次查询对跨境往返十分敏感。

## 6. L3 下单全链路与并发结果

全链路使用隔离用户、地址、购物车、商品、SKU 和耗材，按“加购 → 订单试算 → 创建订单”顺序执行 30 次，不调用支付接口。每个环境完成后删除订单、库存流水、商品、耗材、用户档案和 Auth 用户。

| 测量项 | 新加坡 p50/p95/p99 | 上海 p50/p95/p99 | p95 跨境净增量 |
|---|---:|---:|---:|
| 完整下单链路 | 606.30 / 787.24 / 907.02 ms | 5164.15 / 6295.60 / 7776.44 ms | 5508.36 ms |
| 加购 | 236.18 / 272.31 / 389.48 ms | 1689.93 / 2242.43 / 2246.42 ms | 1970.12 ms |
| 订单试算 | 202.85 / 213.78 / 241.33 ms | 1047.25 / 1591.33 / 3120.23 ms | 1377.55 ms |
| 创建订单 | 171.60 / 363.98 / 424.89 ms | 2413.95 / 2972.97 / 3017.04 ms | 2608.99 ms |

30 次完整链路在两地均为 100% 成功、无业务错误。上海创建订单 p95 为 **2972.97 ms**，已经超过 2 秒强制改造门禁；完整链路 p95 为 **6295.60 ms**，相对新加坡增加约 5.51 秒。

“10 抢 5”复测结果：

| 位置 | 总耗时 | 成功 | 40901 库存错误 | 持久化订单 | 最终可售 | 超卖 |
|---|---:|---:|---:|---:|---:|---|
| 新加坡 | 313.36 ms | 5 | 5 | 5 | 0 | 否 |
| 上海 | 5842.20 ms | 5 | 5 | 5 | 0 | 否 |

并发正确性仍然通过：失败事务没有残留订单，预占耗材恰好 50 克，没有超卖。但上海总耗时约为新加坡的 18.6 倍，锁持有时间和吞吐能力已构成明显风险。第一次把两地并发测试同时启动时，上海在测试夹具初始化阶段遇到一次连接失败；停止对照组并单独运行后通过，因此正式结果均来自无并行干扰的单独采样。

## 7. 最终门禁结论与替代方案

**结论：L3 触发“必须改造”门禁，暂停正式 DNS/公网流量迁移。** 上海只保留 loopback 绑定的预部署环境用于验证；新加坡继续承载现网。这个结论不否定上海主机本身，问题来自跨境 Auth 与数据库多往返被业务链路放大。

| 方案 | 收益 | 工作量与风险 | 建议 |
|---|---|---|---|
| 一：把核心下单事务合并为单个数据库存储过程 | 直接减少当前约 10 次跨境数据库往返，保留 Supabase Auth、Storage 与现有数据位置 | 需要重写核心下单逻辑、幂等与错误映射，并完整复测库存/优惠/退款；购物车和试算仍需单独优化 | 作为短期优先方案先做技术设计和基准原型 |
| 二：数据库迁入中国大陆 | 同时降低商品、购物车、试算、下单等全部数据库路径延迟 | 涉及 PostgreSQL 托管选型、数据迁移、停机/双写、Auth/RLS/Storage 依赖拆分与合规评估，影响面远大于本版本 | 若目标必须长期在境内提供低延迟服务，作为中长期架构方案评估 |

在方案一中，还应把购物车查询合并/批量化，并评估减少每个接口重复远程校验用户的成本。任何改造完成后必须重跑本报告的 L2、L3 和“10 抢 5”门禁，不能只以 L1 热连接 `<80 ms` 判定可迁移。
