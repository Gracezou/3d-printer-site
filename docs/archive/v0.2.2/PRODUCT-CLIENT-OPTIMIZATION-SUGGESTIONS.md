# v0.2.2 前台客户端优化建议

> 文档用途：作为产品 Agent 整理 v0.2.2 正式需求、任务拆分和验收标准的输入材料。  
> 文档性质：建议稿，不直接替代 `CHANGES-v0.2.2.md`。  
> 编写日期：2026-09-10  
> 参考基线：v0.2.1 已完成的预生产验收，以及当前用户端代码实现。

## 1. 建议的版本定位

建议将 v0.2.2 定义为：

> 面向用户端的浏览、选购和结算体验优化版本；以首页品牌表达、购物路径流畅度、移动端体验、可访问性、SEO 和感知性能为主，不修改数据表，不改变核心交易规则。

不建议继续使用“纯前台改造”作为严格边界，因为现有草案中的流水线、服务端缓存、动态 SEO 和后台 `settings` 配置均不属于纯客户端代码。更准确的表述是：

> **前台体验导向、无数据模型变更。**

## 2. 产品目标

本版本应重点改善以下用户问题：

1. 首次进入网站时，能够快速理解网站卖什么、为什么采用按单生产、预计多久交付。
2. 浏览商品时，筛选、排序、翻页和返回操作连续、可预期，不产生“页面卡死”或条件丢失的感觉。
3. 商品存在关联规格时，用户能理解哪些组合可购买，以及下一步应该选择什么。
4. 加入购物车、修改数量、删除商品和进入结算时，界面立即反馈，不因网络请求产生明显迟滞。
5. 移动端完成浏览、选规格、购物车和结算的操作成本明显降低。
6. 页面加载、空数据、网络错误和登录失效均有明确反馈和恢复路径。
7. 为后续搜索引擎收录、性能监控及多语言扩展建立基础。

## 3. 建议范围

### 3.1 P0：本版本建议必须完成

#### A. 首页与品牌表达

沿用现有 T120–T126 的整体方向：

- 优化首页数据缓存。
- 对精选商品与最新商品去重。
- Hero 增加不依赖轮播图的品牌主张、支撑文案和主行动按钮。
- 重排首页内容层级，避免所有区域均使用相同商品网格。
- 增加按单生产流程、打印周期和发货预期说明。
- 增加可索引的品牌、工艺和交付正文。
- 重写栏目标题，避免 eyebrow 与 title 重复以及无信息量的模板话术。

首页内容应优先回答：

- 这是卖什么的？
- 与普通现货商品有什么区别？
- 下单后多久生产、多久发货？
- 用户为什么值得购买？

边界建议：不增加大量 3D 打印技术科普、材质百科或社区型内容，避免首页偏离商城转化目标。

#### B. 商品列表与筛选体验（建议新增 T133）

- 移动端筛选改成抽屉或折叠面板，减少首屏占用。
- 已启用的条件显示为可单独移除的筛选标签。
- 提供明确的“清除全部”入口。
- 更新筛选时保留当前条件和合理的滚动位置。
- 浏览器前进、后退应恢复筛选条件和结果。
- 筛选请求期间保留旧结果，并显示局部加载反馈或商品骨架屏。
- 价格区间增加客户端合法性校验，包括负数以及最低价高于最高价。
- 无结果页面提供移除条件或查看全部商品的快捷操作。
- 结果数量变化通过可访问的状态区域告知用户。

建议验收：

- 筛选后 URL 完整表达当前条件。
- 刷新及浏览器前进、后退后条件不丢失。
- 更新结果时页面无整屏闪白，无意外跳回顶部。
- 360px 宽度下筛选操作完整可用且无横向滚动。

#### C. 商品规格选择体验（建议新增 T134）

不建议简单允许任意规格取消选中。推荐继续使用兼容组合约束，并增强用户引导：

- 用户选择一个规格后，仅禁用不存在或无库存的组合。
- 新选择与旧选择冲突时，自动清除冲突属性，而不是阻止用户切换。
- 明确提示下一项待选择规格，例如“请选择颜色”。
- 提供“重新选择规格”入口。
- 将当前组合、SKU 价格、库存和购买状态集中展示。
- SKU 有独立图片时，规格变化应联动主图。
- 无效组合不能出现“按钮可点击但无法购买”的中间状态。
- 移动端增加底部购买栏，展示价格及主要购买操作。

建议验收：

- 几何氛围灯“大号 + 拼色”“小号 + 黑色”等绑定组合可互相切换。
- 任意选择顺序均不会把用户锁死在原规格中。
- 用户无需理解 SKU 概念即可完成有效组合选择。

#### D. 购物车与结算感知性能（建议新增 T135）

- 购物车首屏尽量由服务端提供初始数据，避免客户端 hydration 后才开始首次请求。
- 数量增减继续采用乐观更新，并合并短时间内的连续请求。
- 删除商品后立即移除，并提供短时“撤销删除”操作。
- 请求失败时只回滚对应商品，不重新加载整个购物车。
- 防止较早的数量请求覆盖较新的操作结果。
- 结算按钮点击后立即锁定并显示明确进度，避免重复提交。
- 地址、优惠、运费重新计算时只更新相关区域。
- 拆分购物车、地址和结算页的大型客户端组件，缩小状态更新引起的重渲染范围。

当前实现说明：购物车已经使用乐观删除，但失败时会完整执行 `loadCart()`，仍可能造成列表跳变；购物车首次加载也完全依赖客户端请求，应作为本项重点。

建议验收：

- 正常网络下点击数量或删除后，界面在 100ms 内反馈。
- 接口失败时只恢复受影响商品，并给出可操作的错误提示。
- 快速连续点击数量不会发生数量回跳。
- 从商品详情进入结算不发生不必要的整页重载。

#### E. 加载、异常与空状态（建议新增 T136）

当前用户端除个人资料页外，基本没有路由级 `loading.tsx`、`error.tsx` 和统一的 `not-found` 体验。建议覆盖：

- 首页。
- 商品列表。
- 商品详情。
- 购物车。
- 结算页。
- 订单列表与订单详情。

统一要求：

- 骨架屏尺寸接近最终内容，减少布局跳动。
- 网络错误提供局部重试，不要求用户手动刷新整页。
- 商品不存在时展示商城风格的 404 页面和返回入口。
- 登录失效时说明原因并保留安全的登录后返回路径。
- 支付结果查询超时后提供重新查询和查看订单入口。
- 空购物车、空订单和无搜索结果均给出合理下一步操作。

#### F. 客户端导航优化（建议新增 T137）

当前用户端存在较多 `window.location.assign()`。建议：

- 站内普通跳转改为 `router.push()`、`router.replace()` 或 `<Link>`。
- 仅支付宝等外部支付跳转保留浏览器级导航。
- 登录回跳、商品详情到购物车或结算等路径避免整页重新加载。
- 导航期间保持明确的按钮状态并防止重复操作。
- 移动端菜单在完成跳转后关闭。

建议验收：

- 站内核心购物路径无非必要整页刷新。
- 登录完成后能恢复用户原购物意图。
- 支付外跳和回跳不受站内导航改造影响。

#### G. 移动端与可访问性（建议新增 T138）

- 统一交互元素的最小触控区域。
- 表单错误与对应字段建立语义关联。
- Toast 和异步结果使用 `aria-live`。
- 弹窗增加 `role="dialog"`、焦点锁定、焦点恢复和 Escape 关闭。
- 补充全站 `focus-visible` 样式。
- 支持 `prefers-reduced-motion`。
- 轮播图支持暂停、键盘操作和当前页状态说明。
- 检查主要文字、按钮和禁用状态的颜色对比度。
- 移动端底部购买栏适配 iPhone 安全区域。

固定验收视口建议：360px、390px、768px、1440px。

#### H. SEO、图片与性能验收（建议扩充 T127–T130）

- 保留动态 sitemap、robots、逐页 metadata 和结构化数据任务。
- 首页、商品详情和商品列表的内容图片优先使用 `next/image`。
- 分类图、购物车缩略图等不应继续依赖 CSS `background-image`，以便获得尺寸约束和图片优化。
- 3D Viewer 保持按需加载，不进入页面首屏 JavaScript。
- 拆分大型客户端组件，优先处理：
  - `checkout-manager.tsx`
  - `address-manager.tsx`
  - `product-purchase-panel.tsx`
  - `cart-manager.tsx`
- 建立移动端真实性能基线，并记录测试设备、网络条件和采集方式。

建议采用以下内部验收目标：

| 指标 | 建议目标 |
|---|---:|
| LCP | ≤ 2.5 秒 |
| INP | ≤ 200 毫秒 |
| CLS | ≤ 0.1 |

指标应以性能预算和回归门槛使用，不将单次本地 Lighthouse 分数等同于真实用户结果。

#### I. 用户端自动化回归（建议新增 T139）

建议引入 Playwright 或同类浏览器测试，至少覆盖：

1. 搜索、筛选、排序及条件恢复。
2. 关联规格的选择与切换。
3. 加入购物车。
4. 修改数量、删除及失败回滚。
5. 登录后恢复购买。
6. 地址选择与结算预览。
7. 提交订单。
8. 支付结果页面。

同时保留移动端关键页面截图，用于发现布局溢出和视觉回归。

### 3.2 P1：时间允许时完成

- 最近浏览商品，但仅保存在本地浏览器，不做跨设备同步。
- 商品详情图片缩放、手势切换和缩略图键盘操作。
- 复制订单号、地址、物流号后的统一 Toast。
- 用户订单状态时间轴视觉优化。
- 登录验证码倒计时、重发状态和邮箱地址纠错提示。
- 地址识别失败时自动聚焦需要补全的字段。
- 商品卡片快速加入购物车，但必须避免绕过规格选择。
- 将颜色、圆角、阴影、按钮、输入框和状态样式收敛为设计 Token。

### 3.3 建议延期

以下需求可能需要新数据模型、服务端能力或独立产品设计，不建议放入本次纯前台体验版本：

- 收藏及跨设备同步。
- 跨设备浏览历史。
- 个性化推荐和“猜你喜欢”。
- 商品评价体系。
- 多币种实际定价与支付。
- 多语言运行时。
- 3D 实时换色预览。
- 用户端售后申请与物流接口集成。

## 4. 对当前 `CHANGES-v0.2.2.md` 的修正建议

产品 Agent 整理正式版本计划时，应同步处理以下问题：

1. 文档仍称 v0.2.1 的 H05、H10、H11、H13–H17 未完成，但 v0.2.1 已验收关闭，应删除该警告和对应遗留风险。
2. T129 的 JSON-LD 转义示例写成了 `replaceAll('<', '<')`。实现要求应明确为将 `<` 转义成字符串 `\\u003c`，并以现有安全实现为准。
3. 将“纯前台改造”调整为“前台体验导向、无数据模型变更”，避免与服务端缓存、流水线和动态 SEO 工作冲突。
4. T131 的“用户端无散落中文字面量”范围过大、收益与改动风险不匹配。建议优先抽取：
   - 公共导航和通用按钮。
   - 订单、支付、退款等交易状态。
   - 通用错误提示。
   - 交期、运费和售后口径。
   - SEO 与邮件复用文案。
5. 页面独有的短文案暂时可以保留，避免为了形式上的零字面量制造大规模无功能改动。
6. T132 多币种缺口设计说明不应阻塞用户端版本发布，可作为收尾文档任务。
7. T122、T124 若要求运营在后台维护文案，就会扩大后台功能范围。产品需在以下方案中明确选择：
   - 本版本使用中文语言包与代码发布，保持前台范围最小。
   - 本版本同步扩展后台 `settings` 管理界面，接受额外后台开发与权限验收。

## 5. 推荐实施顺序

建议按照用户路径和依赖关系实施：

1. 修订版本边界、任务编号和验收口径。
2. 建立设计 Token、加载状态和通用交互反馈基础。
3. 完成首页数据、文案与版式改造。
4. 完成商品列表筛选体验。
5. 完成商品详情规格选择和移动端购买栏。
6. 完成购物车、地址与结算感知性能优化。
7. 完成客户端导航、错误边界和空状态。
8. 完成 SEO、结构化数据、图片与可访问性治理。
9. 增加 E2E、视觉回归和性能预算验收。
10. 完成文案集中化和多币种设计说明等收尾任务。

## 6. 建议的版本完成定义

除原有 `typecheck`、`lint`、单元测试、构建和安全审计外，建议增加：

- 核心购物路径的浏览器自动化测试全部通过。
- 固定四档视口下无横向滚动和关键操作遮挡。
- 站内核心路径无非必要整页刷新。
- 主要页面均具备加载、错误、空数据及未找到状态。
- 商品关联规格可从任意有效组合切换到另一有效组合。
- 购物车正常操作即时反馈，失败能够局部回滚。
- SEO canonical、sitemap 和结构化数据中无 localhost、IP 或错误域名。
- 性能数据有可复现的采集环境、基线记录和回归结论。

## 7. 供产品 Agent 决策的问题

正式整理计划前，需要明确以下产品决策：

1. Hero、交付流程等运营文案是否必须支持后台在线修改？
2. 移动端购买栏只出现在商品详情页，还是购物车和结算页也固定展示主要操作？
3. 删除购物车商品是否需要撤销能力，撤销有效时间设为多少秒？
4. 商品 SKU 图片是否已经具备足够的数据完整度，可支持规格联动主图？
5. 本版本是否正式引入 Playwright，还是继续以人工验收为主？
6. P1 项目是否全部延后，还是选择一至两项作为版本体验亮点？

## 8. 建议主线摘要

v0.2.2 推荐围绕以下链路组织，而不是只按页面罗列需求：

> **首页品牌表达 → 商品发现 → 规格选择 → 购物车与结算流畅度 → 移动端与可访问性 → SEO 与性能验收。**

该组织方式能够让 Beta 用户直接感受到版本升级，同时保持不改数据模型、不重做交易后端的版本边界。
