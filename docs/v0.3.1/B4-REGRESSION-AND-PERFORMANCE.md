## 同条件性能对比

基线为 v0.3.0 `c902b4c`，候选为本批 v0.3.1 代码。两份源码独立生产构建，在同一台 Mac、同一 Chrome、同一本地测试数据库测量；没有在 dev 模式测量。每个页面/宽度先预热一次，再用全新浏览器上下文采样 3 次取中位数。两次测量串行运行，固定 API 模拟延迟 80ms，商品图片使用相同中性占位图，无 CPU/网络节流。

下表单位为毫秒，格式「v0.3.0 → v0.3.1」：

| 页面 | 手机 FCP | 手机 LCP | 桌面 FCP | 桌面 LCP |
|---|---|---|---|---|
| 首页 | 44 → 44 | 340 → 52 | 44 → 40 | 344 → 340 |
| 商品列表 | 40 → 40 | 344 → 344 | 44 → 40 | 344 → 344 |
| 商品详情 | 40 → 44 | 340 → 344 | 40 → 40 | 336 → 336 |
| 购物车 | 40 → 44 | 40 → 44 | 40 → 44 | 40 → 44 |
| 结算 | 28 → 48 | 28 → 48 | 44 → 40 | 44 → 40 |

手机宽 390px，桌面宽 1440px，高 900px。TTFB 中位数范围分别为 3.5–7.0ms / 3.6–7.6ms。购物车点击数量按钮后两次动画帧回调的反馈代理指标：手机 13.6 → 4.9ms，桌面 5.4 → 8.5ms，均为一帧量级；功能用例同时验证数量和金额即时更新。筛选保留文档标记，确认没有引入整页刷新。

**解释边界：**这些是本地实验数据，不是线上用户 Web Vitals，也不是 INP。样本少、没有真实图片/公网请求，布局变化可能改变 LCP 元素；不能把首页 LCP 差异宣传成真实性能提升。结算手机 FCP 增加 20ms，仍在 50ms 内；其他主要页面无明显退化，回归中未观察到明显交互延迟。真实慢网、真实素材与真机体验仍需 T226。

原始记录位于被忽略的 `test-results/performance/v030-baseline.json` 和 `v031-candidate.json`。可复测脚本：

```sh
# 先在本地隔离库准备 tests/e2e/setup.ts 夹具，再启动各自生产构建。
E2E_BROWSER_CHANNEL=chrome pnpm test:storefront:performance http://127.0.0.1:5104 v030-baseline
E2E_BROWSER_CHANNEL=chrome pnpm test:storefront:performance http://127.0.0.1:5105 v031-candidate
```

测量结束使用 `tests/e2e/teardown.ts` 清理专用夹具；脚本只接受 127.0.0.1，不指向 Stage/生产。默认使用 Playwright Chromium，也可通过上例选择已安装的 Chrome；比较双方必须用同一版本浏览器。
