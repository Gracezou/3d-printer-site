# v0.3.1 变更规划：业务通知与用户端购买体验

> 状态：执行中，B0/B1 已完成本地实现与自测，B2/B3 待讨论；基线为已提交的 v0.3.0。执行清单见 [TASKS-v0.3.1.md](./TASKS-v0.3.1.md)。
>
> 版本调整（2026-10-15）：原 v0.3.1「订单状态邮件与开模通知」和原 v0.3.2「购物路径体验」合并为 **一个 v0.3.1 版本**；原 v0.3.2 不单独发布，版本号暂不承载新需求。此前 v0.3.0 文档中的版本序列是当时的历史规划，以本文为后续执行基线。

## 1. 合并后的范围

| 来源 | 纳入 v0.3.1 的内容 | 数据结构 |
|---|---|---|
| 原 v0.3.1 | 独立于登录验证码的业务邮件通道、订单及售后状态通知、意向登记开模通知 | 新增业务邮件队列及必要索引/状态字段，前向兼容迁移 |
| 原 v0.3.2 | 机型筛选与规格选择、购物车与结算交互、账户页、移动端与可访问性、Playwright 回归 | 原则上复用现有交易表；若实现发现必需的改表，先更新迁移与回滚方案 |
| 本次追加的四项 | 机型适配贯穿购买链路；关联规格可理解、可切换；用户端轻量扁平视觉；用准确的实物与交付信息建立信任 | 内容和前端优先复用现有商品、机型及站点资料 |

合并后以一次完整的用户路径验收为准：**找到机型 → 选对商品与规格 → 加购结算 → 查看订单及售后 → 收到相关通知**。v0.3.1 是一次功能与体验合并发布，不将完成邮件或完成界面单独视为版本完成。

## 2. 通知能力

- 登录邮箱 OTP 继续由 Supabase Auth 发送。订单和开模邮件使用独立业务发信身份；发信域按既有决策区分 `auth.` 与 `notify.`，避免模板和退信互相影响。
- 订单通知覆盖支付成功、进入生产、发货，以及售后审核结果和退款成功。仅在业务状态真正持久化后入队；同一业务事件只能生成一条有效通知。取消、失败或重复回调不得误发「成功」邮件。
- 订单邮件显示订单编号、当前状态、必要的下一步操作及站内订单详情链接；不在邮件中暴露完整地址、支付凭据或售后凭证。站内状态始终是权威来源，邮件发送失败不得回滚已完成的订单/退款事务。
- 业务事务内仅写待发消息，定时任务异步发送；队列须有去重键、可重试状态、退避、失败可观测记录和安全的重放方式。发送请求超时或结果未知时，须优先用邮件服务商的幂等键/查询能力核实；无法核实时进入人工复核，不能盲目重发。按现有 `CRON_SECRET` 防护方式接入新任务。
- 开模通知只针对登记该机型的邮箱：机型已开模且已有**可见、在售、真实关联该机型的商品**时才允许入队；仅勾选「已开模」但没有可购买商品不发信。链接指向具体机型或商品，不重复为同一登记人和同一开模事件入队。发送成功后更新登记通知状态；明确失败可重试，未知结果先核实。
- 发信服务商、正式发信凭据和 DNS 配置在实施前落实到部署环境；代码、文档和测试数据不保存真实密钥。Stage 只向受控测试邮箱发信，避免误通知真实用户。

## 3. 用户端四项改动

### 3.1 机型适配始终可见

- 首页缩短首屏视觉区，使机型选择入口及部分商品更早出现；保持现有「按机型找保护壳」的定位。
- 列表沿用已实现的 URL 筛选，补足移动端筛选、已选条件、无结果恢复及切换时的局部反馈；前进、后退和刷新保留条件。
- 列表卡片、商品详情、购物车和订单商品均清楚展示适配机型或适配范围；对兼容组、相近型号的表述以实际商品关联为准，不能由名称推断兼容。
- 用户从机型页进入商品时保留选机型上下文，并提供清晰的切换入口；与当前商品不兼容时先说明原因，不静默下单。

### 3.2 规格选择可理解、可切换

- 延续已决方案 A17：选择新属性与旧属性冲突时，清除冲突维度并提示下一步；提供「重新选择规格」。现有再次点击取消维度行为需按该方案统一，避免两套规则并存。
- 仅把不存在的组合和售罄组合区分标示；当前有效组合的价格、库存、购买状态集中展示。颜色除色块外必须有文字名称，材质/工艺名称给出简短说明。
- 不允许出现看似可购买却无法加入购物车的中间状态。移动端商品详情页提供安全区域内的购买操作入口；购物车和结算页保持页内汇总操作。
- 本版本不要求 SKU 独立图片联动主图；该能力仍属于 v0.4.0，缺少图片时继续展示商品主图。

### 3.3 用户端轻量扁平视觉

- 保持现有品牌色及产品图片，统一用户端容器、按钮、输入框、间距、边框和状态反馈；减少多层卡片、过大的圆角和装饰阴影。
- 商品图和装机图保持展示重点；首页、机型页、列表、详情、购物车、结算、订单与个人中心形成一致的层级。后台的紧凑密度不直接套用到手机端，触控区域、文字对比度和焦点状态须保持清楚。
- 操作完成或失败要就近反馈；加载、空数据、网络错误及不存在状态提供恢复路径。站内导航尽量连续，外部支付宝跳转保留原支付流程。
- 视觉改造不得改写价格、运费、优惠、订单或退款的业务计算。视觉与感知速度分别验收，记录至少一组改造前后的可复现性能数据。

### 3.4 准确的信息建立购买信任

- 商品详情优先呈现实物、装机、开孔及表面纹理照片；没有素材时保留真实商品主图和中性说明，不用生成图冒充实拍。
- 明确展示适配限制、材质/工艺、按单生产流程、交期、运费计算与售后入口；文案与已确定的「7 天内发出」口径保持一致。实际生产能力或运费规则变化时同步更新，不写无法兑现的承诺。
- 首页突出「卖什么、适配哪些机型、怎么生产及何时发出」，减少重复商品网格；订单中心展示可理解的状态进度和下一步操作。
- 运营文案沿用已决方案 A11（语言包 + 代码发布），不为本版本另造后台文案系统。

## 4. 原 v0.3.2 购物路径余项

- 购物车数量和删除应即时反馈，连续操作不回跳；失败仅回滚受影响商品。结算时地址、优惠和运费的变化只更新相关区域，提交订单防重复。
- 账户页以订单和售后状态为核心，地址、资料为次级入口；登录后恢复安全的原购买路径。
- 完善各关键页面的加载、错误、空数据和未找到状态；移动端检查 360/390/768/1440px，支持键盘操作、明确焦点、表单报错关联、动态状态播报与减少动画偏好。
- Playwright 覆盖机型搜索与筛选恢复、关联规格互切、加购改数量及删除、登录回跳、地址/优惠/运费预览、下单、支付结果、售后申请与通知触发的跨层验证。支付和邮件外部通道使用隔离替身；沙箱真实通知另做 Stage 人工验收。

## 5. 版本边界和发布条件

- 不包括 3D 实时换色、SKU 图片联动、商品评价、收藏、跨设备浏览历史、多币种或新的支付渠道；不改变退款金额、运费规则和生产业务状态机。
- 如需创建业务邮件表，应提供前向兼容迁移、旧应用共存及回滚预案，并先在隔离数据库验证。不得因合并版本扩大对生产数据库的直接测试范围。
- 上线前同时满足：业务通知去重/重试和可达性验收；机型与规格不误导购买；购物与售后关键路径浏览器回归通过；主要视口无横向溢出或遮挡；现有支付退款回归通过；Stage 人工完成真实模板、邮件链接和移动端检查。
