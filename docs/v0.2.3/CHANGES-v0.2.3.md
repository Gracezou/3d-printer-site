## 0. 版本定位

为申请支付宝企业商户号，需完成 ICP 备案；备案要求网站由**中国大陆境内服务器**提供服务，因此应用需从新加坡迁至上海。**数据库（Supabase）仍留在新加坡 `ap-southeast-1`**。

本版本要交付两件事：

1. **先验证**跨境数据库延迟是否可接受
2. **再迁移**应用与域名，为备案铺路

顺序不能颠倒——若延迟不可接受，迁移方案本身需要重新设计。

## 2. T160 跨境数据库延迟实测

### 2.1 要回答的唯一问题

> 上海应用 → 新加坡 Supabase 的跨境延迟，是否已经严重到必须执行 `TECH_SPEC.md` §13.2 的「下单事务合并为单个存储过程」改造？

⚠️ **不要预先按最坏情况施工。** §13.2 会重写核心下单逻辑，工作量不小，**必须先测再决定**。

### 2.2 为什么不能沿用 v0.2.0 的性能数据

v0.2.0 曾把商品列表接口从 2.572s 优化到 0.671s。**那是本地开发机访问新加坡 Supabase 的数据**，与「上海机房 → 新加坡机房」是完全不同的网络链路（机房线路可能更好，也可能因跨境管制更差且抖动更大）。**不可照搬。**

### 2.3 为什么这件事对本项目格外重要

`order.service.ts` 的下单逻辑包裹在**单个数据库事务**内（`getDb().transaction()`），事务中约有 **10 次数据库往返**，含 `fn_generate_order_no()`、`fn_reserve_order_stock()` 两个存储过程调用与订单、订单项写入。

跨境延迟在这里有**双重影响**：

1. **用户等待** = 往返次数 × 单次延迟。单次 100ms 时，仅事务部分就约 1 秒
2. **并发能力下降**（更隐蔽也更危险）——事务持有行锁的时间同样等于往返次数 × 单次延迟。锁持有变长会直接削弱并发扣料吞吐。v0.1 验收项 14「10 个并发订单争抢 5 份可售库存，恰好 5 成功」是本项目的核心正确性保证，**迁移后必须复测**

### 2.4 测量范围（三层，必须全部完成）

**L1 裸往返延迟**
- 目标：`SELECT 1`
- 连接方式：与生产一致，**Supavisor `6543` transaction 模式**（用 5432 直连测出的结论不可用）
- 样本量：**≥ 100 次**
- 需区分**冷连接**（含 TCP + TLS 握手，反映建连成本）与**热连接**（复用连接，反映稳态往返）

**L2 真实接口延迟**
- 覆盖：商品列表、商品详情、实时库存、购物车、机型页
- **直接使用既有观测设施**：v0.2.0 的 T115 已为这些接口加了 `Server-Timing` 响应头与 >500ms 慢请求日志，**无需引入任何新工具**
- 与 v0.2.0 记录的基线对照

**L3 下单事务延迟（本次测量的重点）**
- 完整走一遍：加购 → 订单试算 → 创建订单，记录事务整体耗时
- **复测 v0.1 验收项 14**：10 并发争抢可售数量 5，确认仍恰好 5 成功、5 返回 40901、无超卖，并记录总耗时相对迁移前的变化

### 2.5 测量方法要求

每一条都影响结论可信度。

| # | 要求 | 原因 |
|---:|---|---|
| M1 | **报 p50 / p95 / p99，禁止只报平均值** | 跨境问题在长尾，平均值会把抖动抹平 |
| M2 | **分时段采样，至少三个时段**（如 10:00 / 15:00 / 21:00） | 跨境线路晚高峰拥塞明显，单时段数据不足以下结论。**最容易被漏掉的一条** |
| M3 | **不要用 `ping` / ICMP** | ICMP 与 TCP/TLS 路径和优先级不同，Supabase 侧未必响应。必须测真实数据库往返 |
| M4 | 区分冷热连接 | Supavisor 连接复用会掩盖建连成本，只测热连接会低估真实情况 |
| M5 | **设置对照组** | 同一组测试在**现有新加坡服务器**上各跑一遍，作为同区基线，量化跨境净增量 |
| M6 | 测试期间不跑其他重负载 | 2 核 2G 资源有限，并发构建或备份会污染数据 |
| M7 | 记录环境信息 | 时间、出口线路、实例规格、Supabase 区域、连接端口与模式（**脱敏，不得记录密码**） |

### 2.6 判断口径与后续动作

**L1 单次热往返**

| p95 | 结论 | 动作 |
|---|---|---|
| **< 80 ms** | 正常 | **不需要**执行 §13.2 |
| **80–150 ms** | 可用但偏高 | 不立即改造，L3 结果须重点观察 |
| **> 150 ms 或抖动明显** | 不可接受 | 触发 §13.2，或重新评估数据库位置 |

**L3 下单事务**

| p95 | 结论 |
|---|---|
| < 800 ms | 可接受 |
| 800 ms – 2 s | 体验受损，建议改造 |
| > 2 s，或并发验收失败 / 超时 | **必须改造**。并发验收若无法通过属于正确性风险，优先级高于体验 |

**若结论为「必须改造」**：不要直接开工，先在报告中给出两个方案的对比供决策——
- 方案一：按 §13.2 合并下单事务为单个存储过程
- 方案二：数据库迁回境内（工作量与影响面见 `TECH_SPEC.md` §13.2 迁移章节）

### 2.7 交付物

1. **`docs/ops/LATENCY-BASELINE.md`** —— 测量报告，含环境信息、三层的 p50/p95/p99（按时段分列）、新加坡对照组与跨境净增量、并发验收复测结果、**明确结论**
2. 原始采样数据留档（CSV 或 JSON）
3. 若结论为需要改造，附方案一与方案二对比

### 2.8 ⏱️ L1 可以立即开始

L1 不依赖应用部署，只要服务器能连上 Supabase、拿到只读连接串即可执行。

**建议先出 L1 结果**——若 L1 就落在「> 150 ms」区间，整个迁移方案需立刻重新评估，不必等应用部署完成。

- 依赖：T160 的 L1 结果（若 L1 已判定不可接受，先决策再迁）

- 沿用现有发布链路：GitHub Actions 构建不可变 SHA 镜像 → 服务器拉取 → `deploy/release.sh`
- Supabase 保持新加坡 `ap-southeast-1`，`DATABASE_URL` 继续使用 Supavisor `6543` transaction 模式

### 3.1 服务器接入与凭据边界

| 项 | 当前约定 |
|---|---|
| 区域与地址 | 上海，`124.71.145.245` |
| 初始管理账号 | `root`，仅用于首次核查、系统加固和部署初始化 |
| 密码 | 已由用户通过会话临时交付；**不得写入本文档、Git、命令输出或日志** |
| 后续登录 | 初始化后改用 SSH 密钥；确认密钥可登录后再停用密码登录，并轮换已在会话中出现的初始密码 |
| 首次动作 | 先做只读环境盘点与 T160 L1 延迟测试，结果达标后才安装和迁移应用 |

**⚠️ 2 核 2G 的发布策略变化**

内存预算：OS ~300MB + Docker ~120MB + Nginx ~30MB + 应用容器 768MB ≈ 1.2GB / 2GB，**日常运行够用**。但蓝绿发布需同时容纳两份容器（~1.5GB），2G 装不下。

因此**发布时只能「先停后起」，有数十秒停机**。`deploy/release.sh` 的蓝绿逻辑在此规格下无法完整生效，需确认降级路径并在低峰时段发布。有流量后再升配。

**验收**：`/api/health` 返回 `status: ok`、`database: ok`，版本与镜像 SHA 一致。

## 4. T162 域名切换与备案配合

- 新备案域名指向上海服务器
- Nginx vhost、HTTPS 证书、HTTP → HTTPS 跳转
- **`NEXT_PUBLIC_SITE_URL` 是浏览器构建参数**，域名变更**必须重新构建镜像**，只重启容器不会更新前端 bundle（v0.2.2 的 T144 已验证过这个坑）
- 同步更新：`ALIPAY_NOTIFY_URL` / `ALIPAY_RETURN_URL`、Supabase Auth 的 Site URL 与 Redirect URLs、GitHub 仓库变量、页脚 ICP 备案号
- canonical、sitemap、结构化数据随 `NEXT_PUBLIC_SITE_URL` 自动变化，**不得硬编码**
- 备案后接入商会核查网站是否真的由境内服务器提供服务，**必须真迁，不能只把 DNS 指过去**

**⚠️ 发信域名**：若备案域名使用 `.top` 后缀，**不要用它做邮件发件域名**。`.top` 被投递性研究列为高滥用 TLD，会显著加剧 OTP 与订单通知邮件的垃圾箱问题（见 `OPEN-DECISIONS.md` §L1）。建议另备一个 `.cn` / `.com` 专用于发信。

## 6. 遗留风险

| 项 | 说明 |
|---|---|
| **延迟结论可能否定整个迁移方案** | 若 L1/L3 明显超标，「只迁应用不迁数据库」这条路本身要重新评估。这正是先测后迁的原因 |
