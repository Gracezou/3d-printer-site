## 3. 阶段一：构造测试数据

目标：**一笔实付 0.01 元的可下单订单。**

### 3.1 ⚠️ 折扣率的填法极易搞错

代码实现为 `rate = 1 - discountValue`，Zod 校验要求 `0 < discountValue < 1`，提示语是「九折填写 0.9」。

**因此「打 99% 折扣（即减免 99%）」应填 `discountValue = 0.01`，不是 0.99，更不是 99。**

验算：`rate = 1 - 0.01 = 0.99` → `discountAmount = 1.00 × 0.99 = 0.99` → 实付 `1.00 - 0.99 = 0.01` ✅

### 3.2 ⚠️ 运费必须为 0，且不能影响其他地区

v0.1 验收项 9 已确立：**折扣只作用于商品小计，不减运费**。因此实付 = 0.01 + 运费，运费不为 0 就拿不到 1 分钱。

运费规则的匹配逻辑（`shipping.service.ts`）：

```
先找 provinceCodes 包含收货省份的规则（按 sortOrder 升序取第一条）
→ 找不到则取 provinceCodes 为空数组的兜底规则
→ 再找不到则抛错「暂未配置可用的配送规则」
```

**方案：新增一条只覆盖单一省份、`firstAmount = 0` 的运费规则，`sortOrder` 设为最小值。** 测试收货地址填该省份即可命中，其他地区完全不受影响。

> ❌ 不要修改现有兜底规则的金额或免邮门槛——那会影响全站所有订单。

| # | 任务 | 要点 |

## 4. 阶段二：切换支付宝生产配置

### 4.1 ✅ 好消息：不需要重新构建镜像

`ALIPAY_*` 全部是**服务端环境变量**，不带 `NEXT_PUBLIC_` 前缀，不会被注入浏览器 bundle。

因此切换支付配置只需修改 `/opt/3d-printer-site/.env` 并重启容器，**无需走 CI 重新构建**。这与 v0.2.2 的 `NEXT_PUBLIC_SITE_URL` 情况不同（那个是构建期参数）。

### 4.2 需要修改的变量

| 变量 | 说明 |
|---|---|
| `ALIPAY_APP_ID` | 生产 APPID |
| `ALIPAY_PRIVATE_KEY` | 生产应用私钥（RSA2） |
| `ALIPAY_PUBLIC_KEY` | 支付宝生产公钥 |
| `ALIPAY_GATEWAY` | **生产网关，与沙箱不同** |
| `ALIPAY_NOTIFY_URL` | `https://printer.daxiaoxiang.com/...`（异步通知） |
| `ALIPAY_RETURN_URL` | `https://printer.daxiaoxiang.com/...`（同步返回） |
| `ENABLE_MOCK_PAYMENT` | 确认为 `false`（当前已是） |

### 4.3 安全要求

- 生产私钥**只存在于服务器 `.env`**，权限 `0600`
- 不得进入 Git、镜像层、构建日志、聊天记录或截图
- 切换前后执行 `pnpm security:audit` 级别的检查：确认客户端产物无密钥泄漏
- 操作前备份原 `.env`（同样 `0600`），用于回滚

## 6. 阶段四：真实支付与退款验证（本版本的核心交付）

> ⚠️ **这是真实资金。金额虽小，但一旦发生不可通过修改数据库伪造回滚。**
> v0.1 的 T071 早已标注：沙箱退款的返回码与时序可能与生产不同，**必须在生产环境重新验证**。

| # | 验证项 | 判定标准 |
|---:|---|---|
| V01 | 下单 | 订单创建成功，应付金额 **0.01**，状态「待支付」，库存进入预占 |
| V02 | 跳转收银台 | 跳转到**生产**支付宝网关（非沙箱域名），金额、订单号、商品标题正确 |
| V03 | 完成支付 | 真实账户支付成功 |
| V04 | 异步通知 | `/api/payments/alipay/notify` 收到通知并返回**纯文本 `success`**；订单与支付记录转为已支付；库存**只扣减一次** |
| V05 | 同步返回 | `return_url` 正确跳回公开站点（v0.2.1 已修过容器内部地址问题，此处复验） |
| V06 | 通知幂等 | 重放同一条通知，不重复扣料、不重复入账 |
| V07 | 生产任务 | 支付后正确生成 `print_jobs` 记录 |
| V08 | **全额退款** | 后台发起 0.01 元退款，支付宝侧退款成功，订单转为已退款 |
| V09 | 库存返还 | 按后台选择执行；核对库存流水与操作员审计日志 |
| V10 | 退款幂等 | 不可超额退款、不可重复退款 |
| V11 | 证据留存 | 记录订单号、支付单号、退款单号、时间与脱敏截图。**严禁记录私钥、Service Role 或完整个人信息** |

> 因单笔仅 0.01 元，**部分退款无法验证**（最小退款金额限制）。部分退款的生产验证顺延至 v0.3.1 退款引擎重构时，用稍大金额的订单完成。

## 8. 回滚预案

| 场景 | 处理 |
|---|---|
| 支付链路异常 | 恢复备份的 `.env`（切回沙箱配置）并重启容器，**无需重新构建镜像** |
| 已发生真实支付但流程有问题 | 通过**正常退款流程**退回，不得直接修改数据库伪造状态 |
| 数据异常 | 使用阶段前建立的数据库可恢复点 |
| 测试商品被真实用户误购 | 正常发货或全额退款并致歉；这正是 D03 要求显著标识的原因 |

## 9. 验收标准

| # | 验收项 | 判定 |
|---:|---|---|
| 1 | 试算金额 | 下单前试算应付金额恰为 0.01 元 |
| 2 | 生产网关 | 收银台域名为支付宝生产网关，非沙箱 |
| 3 | 支付入账 | 异步通知返回 `success`，订单与支付记录正确，库存只扣一次 |
| 4 | 幂等 | 重放通知不重复扣料、不重复入账 |
| 5 | 同步返回 | 跳回公开站点而非容器内部地址 |
| 6 | 退款闭环 | 全额退款成功，订单状态与库存流水正确 |
| 7 | 数据清理 | 测试商品下架、折扣码与运费规则停用、sitemap 不含测试商品 |
| 8 | 密钥安全 | 生产私钥未出现在 Git、镜像、日志或客户端产物中 |
| 9 | 结论留档 | 可行性结论与证据写入 `OPEN-DECISIONS.md` |

## 10. 遗留风险

| 项 | 说明 |
|---|---|
| **前置条件可能直接不满足** | 若拿不到生产商户号，本版本终止。**这本身是有效结论**，不算失败——它把 `OPEN-DECISIONS.md` §E1 的推测变成了事实，v0.3.0 可据此直接转向备案路径 |
| **测试商品会短暂出现在公开站点** | 商品必须 `on_sale` 才能下单，无法隐藏。缓解手段：显著命名（D03）、单价仅 1 元、测试窗口尽量短、完成后立即下架 |
| **部分退款无法在本版本验证** | 0.01 元订单无法拆分退款，顺延至 v0.3.1 |
| **生产退款行为可能与沙箱不同** | 这正是本版本要验证的内容（T071）。若差异显著，v0.3.1 的退款重构需据此调整 |
| 真实资金不可伪造回滚 | 一切纠正只能走正常退款流程 |
| 定位数据仍未跟上 | 见 `OPEN-DECISIONS.md` A40：线上唯一商品仍是旧定位的氛围灯。本版本再加一个测试商品，站点商品列表会更混乱，**更应尽快处理 A40** |
